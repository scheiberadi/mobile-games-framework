# Sudoku Play Store Release — Design

## Goal

Publish the Sudoku game (`Game02_Sudoku`) to the Google Play Store as its
own listing, distinct from the 2048 game. This is the first Play Store
release for this repo, so it establishes the release pipeline (signing,
bundle build, store assets, submission) that a future 2048 release can
reuse.

## Context

- Google Play Developer account: already exists, but has never
  published an app. New accounts must complete a **closed test with at
  least 12 opted-in testers for 14 days** before Play allows promoting a
  release to production.
- Ads and IAP (AdMob interstitial/rewarded, Remove Ads purchase) are
  fully implemented but gated off via `SudokuController.AdsEnabled =
  false`. For v1 they stay off — ship an ad-free build, flip the flag on
  in a later release once the store presence is established.
- Target API requirement: as of Aug 31, 2026, new Play submissions must
  target API level 36 (Android 16). Unity 6000.5.10f1 ships Android SDK
  platforms 34/36/37, and `AndroidTargetSdkVersion` is already `0`
  (Automatic — highest installed), so this requirement is already met
  with no project setting change.
- Current build path (`AndroidApkBuilder.BuildSudoku()`) produces an
  unsigned/default-signed `.apk` via `BuildPipeline.BuildPlayer`. Play
  requires an `.aab` (Android App Bundle), signed with a real release
  (upload) keystore.

## Scope

In scope:
1. A release build path that produces a signed `.aab` for Sudoku.
2. A release keystore, generated once, kept outside git.
3. Store listing assets: hi-res icon (512×512), feature graphic
   (1024×500), short/full description text, phone screenshots.
4. A privacy policy page, published via GitHub Pages, linkable from
   Play Console.
5. A written runbook for the Play Console steps themselves (app entry,
   Data Safety form, content rating questionnaire, closed-testing
   rollout) — these are manual steps only the account owner can perform
   (account/payment/policy-agreement actions), so this spec documents
   them as a checklist rather than automating them.

Out of scope (explicitly not doing now):
- Turning on ads/IAP for this release.
- Publishing 2048 to Play Store (future work, same pipeline can be
  reused).
- Localization of the store listing (English only for v1).
- Automating the Play Console submission itself (no Play Publishing
  API integration) — this is a manual, guided process.

## Design

### 1. Release build: signed `.aab`

Add `AndroidApkBuilder.BuildSudokuRelease()` alongside the existing
`BuildSudoku()`, sharing the same scene list and icon/identifier setup,
but:
- `EditorUserBuildSettings.buildAppBundle = true` before calling
  `BuildPipeline.BuildPlayer`, restored to `false` in a `finally` block
  so it doesn't leak into the existing `.apk` builds used for on-device
  testing.
- Output path `Builds/Android/mobile-games-framework-sudoku-release.aab`.
- Signing: `PlayerSettings.Android.useCustomKeystore = true`, with
  `keystoreName`/`keystorePass`/`keyaliasName`/`keyaliasPass` read from
  environment variables (`SUDOKU_KEYSTORE_PATH`,
  `SUDOKU_KEYSTORE_PASS`, `SUDOKU_KEY_ALIAS`, `SUDOKU_KEY_ALIAS_PASS`)
  rather than hardcoded — keeps secrets out of the committed script.
  The keystore file itself is generated once via `keytool` (documented
  in the runbook, not committed — add `*.keystore` to `.gitignore`).
- Bundle version code: add an explicit
  `PlayerSettings.Android.bundleVersionCode` bump as part of the method
  (starts at 1; the runbook notes it must increment on every future
  upload). `bundleVersion` (1.0) stays as the existing shared
  `ProjectSettings` value for now.

### 2. Store graphics

Extend the existing procedural-asset approach
(`IconGenerator`/`GradientSprite`) rather than hand-drawing anything
externally:
- A 512×512 hi-res icon: reuse `IconGenerator.GenerateSudokuIcon()`
  logic at higher resolution, saved as a standalone PNG (not wired into
  the app itself — this is a Play Console upload asset).
- A 1024×500 feature graphic: a new small generator function using the
  same gradient/procedural style as the in-game background, with the
  Sudoku icon composited on it.
- Both generated by a one-off Editor script (`Assets/Editor/
  StoreAssetGenerator.cs`, temporary like the diagnostic scripts used
  earlier this session — deleted after the PNGs are exported to
  `docs/store-assets/`).

### 3. Screenshots

Captured from a connected device once the release build (or the
existing debug `.apk`, since visuals are identical) is installed:
`adb shell screencap` for at least: main menu, active gameplay grid,
success popup, high scores page. Saved to `docs/store-assets/
screenshots/`.

### 4. Privacy policy

A single static page, `docs/privacy/sudoku.html` (or `.md`, whichever
renders cleanly via GitHub Pages), stating plainly:
- No account/login, no personal data collected.
- Game progress and settings are stored locally on-device only
  (`PlayerPrefs`), never transmitted anywhere.
- No ads or analytics SDKs are active in this build (true for v1 —
  the policy will need a revision when ads/IAP are turned on in a
  future release, noted as a follow-up).
- Contact: the user's email (already available in this environment)
  for privacy questions, per standard Play Console requirements.

Enabling GitHub Pages itself is a one-time repo-settings change; this
will be called out explicitly at implementation time so the user can
confirm before it's flipped.

### 5. Play Console runbook (manual, documented not automated)

A checklist doc (`docs/store-assets/play-console-runbook.md`) covering,
in order:
1. Create the app entry (package `com.mobilegamesframework.game02_sudoku`,
   title, default language).
2. Store listing: paste description text, upload icon/feature
   graphic/screenshots, link the privacy policy URL.
3. Content rating questionnaire answers (puzzle game, no objectionable
   content, no user-generated content, no in-app purchases live for
   v1).
4. Data Safety form answers (no data collected/shared, given ads/IAP
   are off).
5. App content declarations (target audience/age, ads declaration =
   "No ads" for v1, government apps = no, etc.)
6. Upload the `.aab` to the **Closed testing** track (not Production —
   mandatory first step for this account).
7. Add testers: create a Google Group or use the opt-in email list
   method, share the opt-in link.
8. Wait out the 14-day closed-test window with the 12+ testers, then
   promote to Production from Play Console.

## Testing

- The release build path is exercised the same way the existing
  `.apk` builds are verified: headless batchmode run of
  `BuildSudokuRelease()`, grep `BUILD_RESULT`/`BUILD_TOTAL_ERRORS`.
- No NUnit tests apply here — this is build tooling and static
  content, not engine logic.
- Manual verification: install the resulting signed `.aab`'s
  extracted/`bundletool`-built `.apks` on the connected device (Play
  won't let you sideload a raw `.aab` directly), confirm it launches
  and plays identically to the existing `.apk` build.

## Open follow-ups (not blocking this release)

- Turning ads/IAP on in a later release will require revisiting the
  privacy policy and Data Safety form.
- 2048's Play Store release can reuse this same pipeline
  (`BuildRelease` pattern, keystore-per-app, its own store assets).
